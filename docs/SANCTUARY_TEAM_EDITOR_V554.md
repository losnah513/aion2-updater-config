# Sanctuary team editor · SQL554

The new placement mode is independent of FIXED/PARTICIPATION and INSTANT/APPROVAL. Installation defaults every existing team to MANUAL and verifies unchanged team, force, party, slot, pin and boss-role fingerprints in the migration transaction. Opening or refreshing an editor does not rebalance it. New teams must choose MANUAL or BALANCED; creator placement remains optional.

MANUAL preserves positions and offers one-off PVE redistribution. BALANCED chooses 1–9 forces, then accepts mains, alts and partial rosters. It redistributes unlocked participants on draft changes and successful roster changes from instant admission, approval and departure. A pending request alone does not move anyone. The support screen discloses team-wide moves before its explicit balance-agreement submit button. RANDOM_ALT is prohibited in BALANCED; existing MANUAL reservations, including pins, survive an editor round trip.

The bounded server planner owns eligibility and layout. It respects exact pins, class and difficulty item-level limits, canonical and team-local family separation, and capacity. It distributes mains and headcounts before PVE totals; 1–5 mains in a force share one party. Missing power stays unknown rather than being invented. Stable seeds resolve ties. Search is limited to 30,000 steps and a two-second calculation deadline; impossible or overly constrained layouts fail without dropping people or changing the stored team. This is a bounded heuristic, not a guarantee of a globally optimal partition.

Both preview and final command call the same private input resolver and planner. Preview has no roster writes. The browser coalesces changes after 250ms, permits one calculation at a time and discards stale version/session responses. Final save recalculates from trusted server values under the existing team lock, capabilities, lease, expected revision and receipt boundary. Automatic moves update applied support slot/force pointers and retain the original requested force. Self-departure uses authenticated canonical ownership, never a team-declared relationship. Requests from old editors cannot overwrite a BALANCED or guest roster through an incompatible legacy action.

External guest additions use a team-lifetime slot snapshot, not new character Master rows. Only verified lookup candidates or an existing current Master identity can supply the minimal name/server/class/image/PVE/item-level snapshot. Preparing a draft uses the existing candidate table, a ten-minute lifetime, an actor-serialized 90-active-candidate cap and bounded expiry cleanup. Raw candidate payloads are reduced to the three numerical/root inputs. Saved candidate rows are consumed immediately. Closing/discarding releases owned drafts; a crash leaves only short-lived candidates cleaned by the existing retention job. No additional Cron or Edge is created.

Guest removal and team archive clear the snapshot in the same successful command transaction. Audit payloads omit guest snapshots, and receipts contain no guest profile. Guest-only candidates cannot enter permanent materialization. Existing real Master rows and historical records are not deleted. Guests do not join automatic profile refresh, growth history or rankings. Their stored values remain the lookup snapshot during participation. Team-local MAIN/ALT links require no member code and do not grant login ownership or change the global family graph. The canonical same-family restriction remains an additional constraint.

Guest boss roles retain the existing Kaldrix-only role limits and force-level uniqueness. Cross-force moves release roles; same-force moves retain them. Empty slots and random reservations receive no roles. The public/private roster adapters keep guest occupancy, averages, local relationship labels and images consistent. Quick external additions hand the verified lookup and chosen slot to the same atomic editor.

Deployment order is SQL554, compatible existing `sanctuary-management` Edge API2.6/DB554, then PC/mobile WEB. Cached API2.5/480 and API2.4/458 response negotiation remains. Only the three new service-role RPCs are exposed through the existing authenticated Edge; private helpers remain inaccessible to client roles. The source replacement guards abort on unexpected production function changes. Do not create test sessions or alter operational slots through SQL to verify the feature.

The paired rollback stops new editor previews, guest preparation and new-editor saves through a private feature gate. It deliberately keeps readers, guest cleanup, stored rosters, relationships and BALANCED participation handling intact. Keep the compatible WEB/Edge readers after guests have been stored; blindly reverting to a reader that rejects TEAM_GUEST is not a safe rollback. Repair and re-enable the gate in a reviewed migration. No team/guest row restoration or privilege expansion is part of this rollback.

Validation includes native PostgreSQL full/partial 20/50/90-character layouts; actual command/composer and deferred guard paths; existing populated/pinned team installation; valid/conflicting pins; manual random reservations; instant/pending/approval/departure; guest creation/removal/archive; guest role save/readback; unchanged Master and audit/receipt privacy; replay/stale lease/revision; simultaneous saves; and safe rollback. Browser tests use the real SQL preview through a synthetic local adapter at 1440/390/320/844px, plus existing permission, registration, random-alt and boss-role suites. Synthetic credentials and calendar boundaries are explicitly local fixtures; no operational visitor writes are sent. Final deployment evidence is recorded in the existing Sanctuary project LOG84, Stage16.

# 순위 비교값의 과거 원본 의존 분리 · SQL522

`kinojo_ranking_snapshot_scope_payload_v426`은 영구 캐릭터 ID·PVE/PVP별 마지막 성공 조회일과 그보다 이른 직전 성공 조회일을 `character_history`에서 직접 읽었다. 마지막 조회가 오래전이면 원본을 삭제할 때 비교값도 사라졌다. 기존 v426 요약표는 서버·이름을 키로 사용하므로 현재의 영구 ID 기준 조회에 그대로 연결하면 동명·이름 변경·서버 이전의 의미가 달라진다.

## 저장과 조회

- 새 private 숫자 상태는 영구 ID·PVE/PVP별 최대 두 조회일만 보존한다. 전투력·아이템레벨·조회일·관측 시각·출처 ID만 저장하고 raw JSON·이름별 복제·장비 상세는 저장하지 않는다.
- 동일 날짜에서는 기존과 같이 created_at DESC, id DESC의 마지막 성공을 선택한다. 전투력 최대값을 선택하지 않는다. 순위의 다른 값·평가·권한·응답 형태는 유지한다.
- 이력 INSERT 및 관련 UPDATE가 같은 트랜잭션에서 숫자 상태를 반영한다. 캐릭터별 advisory lock을 사용하고, 신원 변경 시 두 캐릭터 잠금을 정렬해 확보한다. 늦은 조회·실패·수치 수정·분류 변경·신원 정정도 반영한다. 값이 같은 상태는 다시 쓰지 않는다.
- 원본 보존 DELETE는 숫자 상태를 삭제하지 않는다. source_id는 과거 관측의 출처 표시이며 살아 있는 원본을 요구하는 FK가 아니다. 캐릭터 자체가 삭제되면 해당 숫자 상태는 FK CASCADE로 제거된다. 출처를 다시 읽는 신규 소비자는 추가하지 않았다.
- 기존 이름 기반 v426 상태와 writer는 다른 기존 소비자를 위해 유지한다. 이번 변경은 영구 ID를 쓰는 순위 비교 소비자의 전환이며 두 오래된 표를 무조건 합치거나 삭제하지 않는다.

## 검증

- 실제 기존 순위 함수와 새 함수의 JSON 전체를 본캐/전체·기본 레기온/전체 레기온 4조합에서 비교한다.
- PGlite 회귀: 하루 여러 조회의 마지막값, PVE/PVP, 동명 캐릭터, 이름 변경·서버 이전, 늦은 응답, 값 수정·실패 전환·신원 정정·gear 변경·null 시각, 40회 반복 수집의 저장 상한, 원자 rollback, ACL, 원본 삭제 뒤 숫자 유지가 통과했다.
- 원본 삭제 뒤 새 조회가 들어와도 보존된 마지막 수치가 직전값으로 이어지는 검증을 포함했다. 기존 character-history-stable-identity 통합 회귀에도 SQL522를 적용하여 실제 Worker adapter → Parser → Master/source/history/rollup/review/event 경로, 1,000행 쓰기, 재시도·실패 원자성을 함께 검증했다. 공식 HTTP와 접수 전송은 합성 입력이며 운영 벤치마크가 아니다.
- 운영 적용은 원본·Master·평가 표의 쓰기를 잠시 잠근 같은 트랜잭션 안에서 4범위 전체 응답 hash가 일치해야 성공하도록 했다. 실제 적용이 이 검증을 통과했다. Security Advisor 기존 5항목 그대로, 신규 0.
- 운영 숫자 상태 367행, 캐릭터 168개, 직전 조회일 비교 177개, 물리 106,496B. 적용 후 전체 DB 388,918,419B. 이번 단계는 원본을 삭제하지 않았으며 즉시 용량 절감으로 보고하지 않는다.

## 복구와 남은 작업

Rollback은 같은 4범위의 결과가 원본 기반 함수와 동일한 경우에만 되돌린다. 이후 보존 정리로 필요한 원본이 사라졌다면 전체 rollback을 취소해 숫자 비교값이 조용히 없어지는 일을 막는다. 그 경우 원본 복원 또는 새 구조와 호환되는 수정이 필요하다. 코드 revert가 삭제 원본을 복원하지는 않는다.

순위의 평가 문구는 아직 growth_reviews와 character_history를 연결한다. 현재 평가 상태를 영구 ID로 분리하는 작업, 다른 현재 상세·스킬·재처리·실패 큐 참조의 분리와 오래된 원본 정리는 남아 있다. 관리자 상세 30일, 주·월 숫자 보존, 기존 정리 예약은 변경하지 않았다. 운영 브라우저 인증 검수는 수행하지 않았으며 DB 내부 계약 검증으로 기록한다.

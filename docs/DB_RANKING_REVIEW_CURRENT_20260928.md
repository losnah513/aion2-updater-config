# 순위 평가 문구의 원본 의존 분리 · SQL523

순위 후보 조회의 평가 문구는 `growth_reviews`를 현재/이전 `character_history`에 연결해 읽었다. 숫자 비교를 분리한 SQL522에 이어, 마지막으로 검증된 평가를 영구 캐릭터 ID별로 유지하고 순위 조회에서 두 원본 표를 직접 읽는 경로를 제거했다.

## 계약

- `private.kinojo_ranking_review_current_v523`은 캐릭터별 PVE/PVP 및 분류 미확정 상태를 각 하나씩 유지한다. 마지막 평가 ID, 현재/이전 출처 ID, 문구·라벨·상태·시각만 보존한다. 장비나 평가 raw JSON은 복제하지 않는다.
- 기존 `created_at DESC, id DESC` 순서와 null 시각 정렬을 유지한다. 분류 미확정 평가도 기존 `review_updated_at` 집계에 기여하므로 별도 UNKNOWN 슬롯으로 보존하지만 PVE/PVP 문구로 표시하지 않는다.
- 현재/이전 이력의 캐릭터 ID 일치 조건을 유지한다. 원본이 이미 정리된 경우에는 해당 출처의 검증된 현재 상태가 있어야 신원을 재사용한다. 이름만으로 연결하지 않는다.
- 평가 INSERT/수정, 이력의 신원·분류 수정은 같은 트랜잭션에서 반영한다. SQL522 잠금 뒤 SQL523 잠금을 얻고 신원 이동은 새 ID 상태를 먼저 확보한다. 값이 같은 상태는 갱신하지 않는다.
- 보존 DELETE 후에도 마지막 평가는 유지한다. 출처 ID는 과거 메타데이터이며 살아 있는 raw FK가 아니다. 캐릭터 자체 삭제 시에만 해당 상태를 CASCADE 삭제한다. 기존 이름 기반 요약과 다른 소비자는 유지한다.
- 이력 참조 인덱스 두 개를 추가해 평가 writer와 신원 정정의 탐색을 지원한다. private 테이블 RLS를 켜고 클라이언트·service_role 직접 권한 및 helper 실행 권한을 부여하지 않았다.

## 검증과 운영

- PGlite는 네 범위의 순위 JSON 전체를 기존 함수와 비교한다. 평가 수정·순서 변경·동명·이름/서버/신원 변경·잘못된 이전 이력·지연 이력 입력·분류 변경·UNKNOWN 시각·null·반복 저장 상한·원자 rollback·ACL을 검증했다.
- 원본 삭제 후 문구 유지, 이후 문구 수정과 새 평가, 원본 평가 삭제 후 신원 이동을 검증했다. 새 조회 함수에 두 원본 표의 직접 참조가 없음을 검사한다.
- 기존 Worker adapter → Parser → Master/source/history/rollup/review/event 통합 회귀에도 SQL523을 포함했다. 1,000행 쓰기와 재시도·실패 원자성 PASS. HTTP/접수 전송은 합성 입력이며 실제 운영 인증 또는 벤치마크 검증은 아니다.
- 운영 migration은 같은 잠금 트랜잭션에서 본캐/전체 및 기본/전체 레기온의 네 범위 응답 hash가 일치해야 성공한다. 실제 적용이 통과했다. Security Advisor 기존 5항목 그대로, 신규 0.
- 운영 평가 190행·168캐릭터, 상태 81,920B, 새 인덱스 합계 270,336B. 이번 단계에서는 원본을 삭제하지 않았다.

## 용량과 후속

적용 후 전체 DB는 **396,045,459B**로 390MB 목표를 재초과했다. 새 상태/인덱스 합계는 352,256B다. 같은 날 07:00 UTC(16:00 KST) 시작한 새 수집을 확인했고, 실행 요약은 306행/8,331,264B, snapshot 74,825,728B, payload 41,263,104B, ranking_entries 6,561,792B였다. 전체 증가분을 이번 마이그레이션이나 특정 한 원인으로 단정하지 않는다. 이 시점의 진행 세션은 0이었다. 순간적인 용량 회수를 반복해 안정화 완료로 표시하지 않는다.

순위 읽기의 이력 의존은 분리했지만, 평가 생성 함수의 이전 이력 탐색과 현재 상세·스킬·stat·재처리·실패 큐의 참조는 별도다. 이 소비자들을 최소 상태로 전환하고 보호 집합을 다시 확인한 뒤 보존 기간을 넘긴 history/review/payload/snapshot을 정리해야 한다. 관리자 상세 30일·주/월 숫자 보존·기존 정리 예약은 바꾸지 않았다.

Rollback은 원본 기반 함수로 되돌려도 네 범위의 결과가 같을 때만 허용한다. 원본 소실로 결과가 달라지면 트랜잭션 전체가 취소되어 현재 문구를 지킨다. 원본 복원 또는 새 구조와 호환되는 수정이 필요하며 코드 revert만으로 삭제 데이터를 복구하지 못한다.
